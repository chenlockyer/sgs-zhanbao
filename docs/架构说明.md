# 架构说明：为什么把校对和写稿拆开

## 一句话

语音转文字有错字，是**输入质量问题**；写战报是**内容提炼问题**。
两件事交给同一个模型、同一段提示词做，会互相污染。所以拆成两个独立上下文。

```
逐字稿 txt
   │
   ├─ 步骤 1  校对（两次独立调用）
   │     1a 逐段找错：输入片段 + glossary.yaml，输出候选修正
   │     1b 终审复核：把候选连同原句上下文交给第二个上下文逐条判断
   │         → 否决「无血条→无懈条」这类断词误伤，否决把玩梗当错字
   │     输出：修正清单 + 校正后逐字稿
   │     提示词：data/prompts/proofread.md、verify_corrections.md
   │
   ├─ 步骤 2  提取（独立上下文，提示词里没有一句纠错）
   │     输入：校正后逐字稿 + 赛果
   │     输出：report.json
   │     提示词：data/prompts/extract_report.md
   │
   └─ 步骤 3  渲染
         输入：report.json（不含任何校正内容）
         输出：成品长图
```

## 拆开解决的三个具体问题

**1. 纠错指令会挤占写稿的注意力。**
早期 `extract_report.md` 里塞了「常见转写错误对照」「修正同音错字要有把握」，
模型每写一段都要分心判断「这个字要不要改」。现在写稿模型只面对已经干净的文字。

**2. 纠错标准不该由写稿模型临时拍板。**
校对要保守（没把握就不改、玩梗必须保留、术语按表还原），
写稿要放开（把关键回合写成短而有信息量的一句话）。两种取向放在一起必然折中。
现在校对只对 `glossary.yaml` 负责，写稿只对「不编造、忠于原文」负责。

**3. 修错了可以只重校、不重写。**
校对产物独立落盘：`<stem>.corrected.txt` 和 `<stem>.corrections.json`。
发现漏校/误校，改完重跑 `proofread` 即可，战报提取和版式都不用动。

## 为什么「每个片段一次调用」而不是整篇一次

1.5 小时的稿子约 2.3 万字，整篇塞进去模型会漏掉后半段的错字（注意力稀释）。
按 1800 字左右切块，每块一次调用，每块都带完整术语表：

* 每块上下文足够小，校对更专注
* 术语表每次都完整参与判断，不依赖模型记忆
* 某一块失败只影响那一块（记进 `failed_chunks`，其余照常出稿）

提取步骤同理：先逐块局部摘要保住细节，再把摘要 + 原文首尾喂给最终提取。
短稿（低于 6000 字）会自动跳过摘要，省一半 token。

## 哪些修正会被真正应用

`proofread.md` 要求模型给每条修正标 `confidence`：

| 置信度 | 处理 |
|---|---|
| `high` | 替换进校正稿（只影响喂给写稿模型的文字） |
| `medium` / `low` | **不替换**，只在 `corrections.json` 里标「待确认」，留给人判断 |

没把握的字宁可不改。此外还有四道硬校验，模型骗不过去：

1. `wrong` 必须**逐字出现在本片段原文里**，否则丢弃（防幻觉、防概括）
2. `wrong == right`、超长、空值直接丢弃
3. 终审否决的修正降级为「待确认」，不写进逐字稿
4. 替换时统计实际命中次数，`applied == 0` 的标「未应用」，不会假装改过

## 替换为什么必须「一次扫描、长词优先」

逐条替换会互相打架，两个真实踩过的坑：

* 先把「丈八蛇矛」→「丈八长矛」，再让「丈八」→「丈八蛇矛」扫一遍，
  得到 **「丈八蛇矛长矛」**
* 「无中生有」里的「无中」若被当成错字替换，会变成 **「无无中生有」**

所以 `proofread._apply_one_pass()` 是单次扫描：从每个位置起只匹配**最长**的那个
`wrong`，替换后直接跳过替换结果，后面不会再被二次改写；遇到「这里已经是正确写法」
的位置照抄过去、不计入 `applied`。

## 校正内容为什么不进战报

**战报正文只写比赛本身**，语音修正清单是给作者复核的中间产物，不是读者要看的内容：

* `report.json` 里没有 `corrections` 字段，渲染层也没有「修正汇总」区块
* 修正清单只留在 `<stem>.corrections.json`
* `report.meta.proofread` 只记录统计（采信/待确认各多少处、是否有失败片段）

## 模型选型：为什么是 DeepSeek（以及为什么可以换）

* 支持 `response_format: json_object`，结构化输出可校验，不用正则抠 JSON
* 中文赛事黑话理解到位（「曹敢三」「路边一条」都能正确保留）
* 便宜、快；1.5 小时转写稿全流程约 3 万 tokens

但**没有绑死**：`SGS_LLM_BASE_URL` / `SGS_LLM_MODEL` 可以指向任何兼容 OpenAI
Chat Completions 协议的网关。`llm.py` 只用标准库 `urllib`，不依赖 SDK。
对不支持 `response_format` 的网关，`chat_json()` 有「上次输出不是合法 JSON，
请重出」的兜底重试路径。

## 为什么出图用 HTML/CSS 而不是生图模型

生图模型对中文的顽疾是**文字大量变形**，成品完全不能用。HTML/CSS 渲染：

* 文字 100% 准确、清晰
* 版式精确可控：尺寸、间距、字号都是代码里的常量
* 内容变了只换数据，不动版式
* 2x 出图，手机上看不糊

所以现在的做法是：美术素材只当背景，**所有文字由代码画上去**。

## 维护方式

| 想改什么 | 改哪里 | 要重跑 |
|---|---|---|
| 某个队名/武将/装备的正确写法 | `data/glossary.yaml` | `proofread` |
| 校对的判断尺度（改多狠、什么算错） | `data/prompts/proofread.md` | `proofread` |
| 战报怎么写、要哪些字段 | `data/prompts/extract_report.md` | `extract` |
| 版式 / 字号 / 坐标 | `render.py` 顶部常量 + CSS | `render` |
| 配色（文字/描边/页底） | `config.Palette` 或 `SGS_COLOR_*` | `render` |
| 素材本身（头尾中部条） | `scripts/build_art.py` 或 `SGS_ART` | `render` |
| 换整套美术素材 | `SGS_ART=<目录>` 或 `build_art.py` | `render` |

三者互不影响：改战报提示词不需要动校对，补术语表不需要动提示词。
